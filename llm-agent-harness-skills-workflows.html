LLM, Agent, Harness, Skills, Workflow: The Full Stack

Five words everyone uses loosely, defined precisely against each other — from the model that only predicts text, up to the fixed sequence that might call it once, many times, or not at all.

september 2026 · notes

In earlier notes I covered the ReAct loop, and in another piece how tools and MCP fit in. The question I kept getting asked after both — and kept answering slightly differently each time — was how the five pieces actually stack: the model, the agent, the harness, the skills, and the workflow around all of it. This is my attempt to fix that, cleanly, once.

The stack, bottom to top

Read it bottom to top: the model is the smallest, most passive thing in the stack. Everything above it adds a capability the model doesn't have on its own — memory of what just happened, the ability to actually do something, knowledge of how to do it well, and — at the very top — a shape decided by a person instead of decided live.

LLM — predicts text, nothing else

Start here because it's easy to forget: a language model takes text in and produces text out. That's the entire capability. It can't read a file, run a command, remember yesterday's conversation, or check whether what it said is true. Every other layer in this stack exists to compensate for one of those gaps.

Agent — the loop that gives the model memory and initiative

An agent is a program that calls the model repeatedly, feeding each response back in as input to the next call, so the model appears to "remember" and "decide" across multiple steps. The shape most agents take is ReAct: the model proposes a thought and an action, something executes the action, the result comes back as an observation, and the loop continues until the model produces a final answer instead of another action.

The critical thing an agent is not: it's not the thing that actually runs commands or touches files. The agent is the decision loop. Something else does the touching.

Harness — the thing that actually does anything

This is the layer most often left out of the conversation entirely, and it's the one that matters most for safety. The harness is the ordinary program wrapped around the loop that reads the model's proposed action and actually executes it — runs the shell command, writes the file, calls the API — then hands the result back.

The model never does anything. It describes an intent as text. The harness is the only part of the whole stack with real permissions, and every security question in this space — what's this agent allowed to touch, what needs a confirmation prompt, what's sandboxed — is a harness question, not a model question.

This is also why two products built on the "same model" can behave completely differently: the model is identical, but one harness might allow unrestricted shell access and another might restrict it to three whitelisted read-only commands. The intelligence is shared; the danger (or safety) is entirely in this layer.

Skills — instructions, not new capability

A skill is a file of guidance the agent reads into context when a matching task shows up: which tools to use for this kind of job, in what order, which mistakes to avoid, what "done" looks like. Crucially, a skill doesn't grant the agent anything it couldn't already do — the harness already exposed the tools. What a skill adds is accumulated judgment about how to use them well, written down once instead of re-derived from scratch on every task of that shape. My own skills-for-microservices repo is this exact pattern: the tools (file search, reading configs) already existed; the skill is the procedure for using them well specifically when a change spans several services.

Workflow — the shape decided before anything runs

Everything above is about a model making live decisions. A workflow is the opposite move: a human decides the sequence of steps ahead of time, in ordinary code. Step one always runs, then step two, then a fixed branch on a condition. Nobody — model or otherwise — is choosing what happens next at runtime; the control flow is just a program.

The useful test: could you draw the whole thing as a flowchart before running it once, and would that flowchart still be accurate afterward? If yes, it's a workflow. If the actual path depends on something the model decided mid-run that you couldn't have drawn in advance, it's an agent.

A workflow can call an LLM inside one bounded step — "summarize this ticket," "classify this request" — without that step controlling the overall sequence. And a workflow can contain an entire agent as one of its steps, handing off to the dynamic loop only where the right steps genuinely can't be enumerated in advance, then resuming the fixed sequence once the agent finishes. That's the dashed line in the diagram above: the workflow is the outer shape, and an agent is one thing that can happen inside it.

One request, through all five layers

Concretely — "resolve this ticket that touches three services":

  • Workflow: ticket in → triage → resolve → open PR → run CI. Fixed, decided in advance.
  • Agent: inside "resolve," a loop runs, because nobody can pre-write which files matter or how many attempts it takes: read, search, edit, test, read the failure, fix, re-test.
  • Harness: every read, edit, and test run is a real action — a file actually changes, a process actually runs — executed by the program wrapping the loop, under whatever permissions it was granted.
  • Skills: because the ticket spans services, a cross-service skill loads into context — which service owns what, which flows are legacy — so the agent isn't rediscovering that from zero.
  • LLM: underneath every one of those steps, a single model call predicting the next useful token.

Five different words, five different scopes, one coherent system. Most confusion in conversations about "agentic AI" comes from someone using one of these words to mean the whole stack. Ask which layer they actually mean, and the conversation gets a lot shorter.
